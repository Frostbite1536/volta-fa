Desk research only: nothing here was run by us. All numbers are the fork's own reports.

Source: `jmnargi/Strata-V100` at `4c56f005` (2026-11-03, MIT), a V100 fork of `Niko1221/Strata`. Files read:
- `README.md`;

Context: an r/v100 user thread with speed reports.

## What it is, and why it does not fit volta-fa

Strata is a runtime for one model, Qwen3.8 Flash-Next (MoE), built partly on ggml. Experts live in system RAM or on
SSD, with a VRAM expert cache. On the fork's 2× V100 16 GB rig, a ~40 ms decode window breaks down as follows
(`2026-10-20-v100-sm70-speed-stack`):

| part of the window | time |
| --- | --- |
| GPU compute | ~20 ms |
| missed experts over PCIe | 6.5–8.0 ms |
| CPU-pool rows | 4.2–5.2 ms |
| the host's per-layer plan (doorbell) | 1.4–1.6 ms |

Neither upstream Strata's 6-switch nor its 13-switch Volta kernel stack moved decode outside run-to-run noise. The
bottleneck is offload, not kernels.

The owner's box (8× V100 32 GB, 256 GB of VRAM) does not need expert streaming: ReVolta serves the same model from
4 such cards (`revolta-2026-11-06.md`).

**Quality is not established by what is published:**
- **Tail skip on by default.** Since 0.1.42, `STRATA_ROUTE_TAIL_SKIP=7` drops missed experts that every token of a
  verify window ranks 7th or lower.
- **The Volta expert path changes answers:** FP16 activations instead of q8_1.
- **Not reproducible run to run.** The fork says so: the adaptive tier decides per window whether an expert runs on
  the GPU or the CPU, and the two round differently.
- **Speed claims in the thread are inconsistent.** One user corrected their own P100 prefill from 1,350 to
  260–280 tok/s.

**Not useful for us:**
- expert streaming and caching, the layer-split pipeline;
- the QSA prompt attention: model-specific sparse attention on the same `mma.m8n8k4` llama.cpp's FA already uses;
- the tensor-core expert GEMM: +10% over dp4a MMQ, covered for us by P-9.

## Lesson 1: signal a finished copy from the device, not with a host callback

**Setup.** In the fork's `--pcie-mode dma`, a copy runs on a second stream while a captured graph spins on a
mapped-memory flag that says the copy has landed.

**Two ways to set the flag:**
- **Host callback** (`cudaLaunchHostFunc`): the driver's callback thread sits between copy and flag. On a six-core
  host that also runs the expert pool, its latency exceeded the copy: **19.07 ms/token**.
- **Device-raised flag:** a one-thread kernel queued after the copy on the same stream writes the mapped flag with
  a system-scope fence: **14.56 ms/token**. The copy kernel in the layer's chain measured 15.6.

**The trap they document.** A host `cudaMemcpyAsync` queued to a card whose graph spins on a host flag can block in
the driver until the window ends (upstream Strata issue #31). Their safe form is copies inside the captured graph,
ordered by events.

**For us.** This matters for P-7's known limit (large staged copies block the host on staging-buffer reuse) and for
Phase 3 signalling. Any spin-waiting kernel we write must not depend on a host-issued copy into the same device
while it spins. INV-P2P-002 already requires stream/event ordering; this adds the reason a host callback is the
wrong signal inside a hot loop.

## Lesson 2: a rounding-only control arm in distribution checks

For their sm_70 prompt-attention kernel, the fork measured KL against the old path and against two controls that
only change rounding order (`2026-10-03-v100-prompt-attn`):

| comparison | KL at 8.5K / 33K / 99K |
| --- | --- |
| old path vs new kernel | 0.028 / 0.040 / 0.116 |
| control: BF16 path change | 0.026 / 0.051 / 0.090 |
| control: prefill chunk 2048 | 0.023 / 0.035 / 0.038 |

The kernel itself agreed with the old one to 4.4e-7 relative per row on model data. Most of the KL is the model
amplifying rounding differences.

P-9 compared against an FP32 reference (dequantize + SGEMM), which is the stronger test. Where we compare two GPU
paths (perplexity or KLD "within noise" claims), add a rounding-only control (for example another ubatch size) so
the noise floor is measured, not assumed.

## Lesson 3: independent evidence for P-9 design D2

On sm_70, Strata's FP16 prompt path gave non-finite logits from layer 0 for `UD-Q4_K_XL`, starting in a Q5_1 down
projection (Strata issue #879, `docs/NVIDIA_V100.md`). That is the FP16 activation overflow that D2's per-slice
power-of-two scaling exists to prevent (`docs/design/P9-small-batch-qmatmul.md`, "Phase 2, fourth part"). Patch
0008 does not route Q5_1, so there is nothing to change; it is a second, real-model reason D2 is required.
